# Architecture

## About this repo's standalone design

This app used to live inside a larger internal monorepo (now archived) alongside unrelated apps and the SDK's own source. It was pulled into its own repo mainly for operational separation: this app needs live production credentials (`AGENTIC_PARTNER_ID`/`AGENTIC_ADMIN_SECRET`) and its own CI/release cadence, which the zero-dependency SDK repo has no reason to carry, and vice versa.

The eval suite's adversarial content — jailbreak prompts, the exact refusal phrasing Nova relies on — is published here on purpose, as worked reference material for building an eval harness for your own live avatar app. See "About the eval harness as a reusable pattern" below.

Because of that split, the SDK dependency couldn't stay a relative disk path into a sibling checkout. Three alternatives existed: publish the SDK to the npm registry (it's deliberately private on npm — it ships to browsers via jsDelivr's GitHub-CDN mode instead), add it as a git submodule (extra clone/update friction for a plain `npm install` workflow), or vendor it. `scripts/fetch-sdk.mjs` vendors it: it downloads the SDK's `src/` tree from jsDelivr at a pinned tag into a gitignored `vendor/sdk/`, the same CDN and pinning scheme the docs site's own browser-side `connect.js` already uses. This runs automatically via `postinstall`, so `npm install` alone leaves the repo fully runnable — no other Kaltura repo needs to exist on disk. (Node has no stable way to import directly from a network URL at runtime, which is why this is a fetch-once-to-disk step rather than a live import.)

The docs-site checkout itself stays a second, separate clone rather than living inside this repo, so the admin secret in this repo's `.env` never sits in the same working tree as anything meant to be public. See [docs/GETTING-STARTED.md](GETTING-STARTED.md) for how to set that up, and `site-root.mjs` for the resolution logic.

## About the two backends and Knowledge Path A

`provision.mjs`'s management-plane calls (create/update/delete the intellect, avatar, agent, tools, and knowledge records) go through the SDK's `Management` class. The eval's headless conversational calls (`tests/eval/transport.mjs`) hit the Genie conversation endpoint directly (`AGENTIC_GENIE_URL`, defaulting to production) to POST tool-call ACKs — something `Management`'s own `Conversations` resource has no built-in path for, since only a live browser session's `respondToTool()` normally does this. The chat-mode personas take a second path (`tests/eval/chat-transport.mjs`): they drive the SDK's real `KalturaChatSession` — the exact class the site's chat mode ships — so its `respondToTool()` and `setDynamicPrompt()` wire contracts are exercised as shipped, not re-implemented.

Nova's knowledge base is wired via what this SDK calls Knowledge Path A: mint a category and a knowledge record with `knowledge.addRecord()`, upload each of the site's 16 pages into it with `knowledge.uploadMarkdown()` (front matter stripped first — it's Eleventy build metadata, not doc content), then pass the record's id as `knowledge_ids` on the intellect body. This corpus is trusted content, not user-supplied — it's the same 16 site pages an admin reviews and merges through this repo's own PR process, uploaded server-side by whoever runs `provision.mjs`, same trust tier as the persona prompt itself. The only untrusted-at-runtime inputs in this system are the visitor's own turns and the live per-page context (the `page_context` request variable, pushed via `session.setDynamicPrompt()` — see `highlighter.js`/`navigator.js` in the site repo) — both assembled in the visitor's own browser, never the static KB corpus.

Before the intellect create/update call, `provision.mjs` runs the SDK's `lintPersonaIdentity()` over the persona name, opening phrase, base directive, and prompt values. It catches a rename that only touched some of those — e.g. `PERSONA_NAME` changed but `buildBaseDirective()` or a prompt still says the old name. It's warning-only and never blocks provisioning: findings log as `⚠ persona identity lint findings:`, a clean run logs `✓ persona identity lint clean`. The wiring (and Nova's own name-only shape passing clean) is covered by `tests/eval/provision.test.mjs`.

RAG search over a freshly-uploaded, not-yet-indexed corpus can loop for 45-90+ seconds, and there's no reliable signal yet that tells `provision()` when indexing has actually finished: `kaltura.knowledge.isIndexed(recordId, admin)` reads the knowledge record's own container status, which reports ready the instant the record exists, not once its entries have indexed (`knowledge.corpusStatus` doesn't help either — it only counts entries that exist, not whether they've finished embedding). A real per-entry check (`kaltura.knowledge.entryStatus()`) is coming, with general rollout expected in early September 2026 — not yet GA, so `provision()` doesn't rely on it. Until then, `provision()` budgets a fixed best-effort wait (`INDEX_WAIT_MS`, 80s) *before* the intellect is ever created or updated, then writes `use_knowledge_base:'on'` into that same single add/update call — never a follow-up `setCapability()` patch. This matters because this SDK's own [docs/CLIENT-COMMANDS.md § Gotcha 2](https://github.com/kaltura/intelligent-agents-sdk/blob/main/docs/CLIENT-COMMANDS.md) documents that partner config is Redis-cached ~24h server-side: flipping a capability on an *existing* intellect won't reach converse time until that cache expires, and a two-step create/update-then-setCapability sequence risks the cache latching onto the transient value from step one instead of ever seeing step two. Resolving and writing once removes that race for a fresh create (no cache entry yet, so the write lands immediately); a `--reuse` redeploy of an intellect the runtime has already cached is still subject to that ~24h propagation delay regardless of how the write is sequenced — a platform limitation, not something this file can work around.

A `--reuse` redeploy first deletes the previous run's knowledge category, record, and entries before uploading the new set. Without that teardown, every redeploy would silently leave the prior corpus orphaned in the account — `server/agent.json`'s ids get overwritten the moment the new ones are written, so nothing could find the old ones afterward to clean them up. Verified live: the category and all of its entries are reliably deleted this way (a get-after-delete on either 404s). The record object itself is a separate, smaller leak — see "Known limitations" below.

## About redeploying and evaluating via GitHub Actions

Two workflows in `.github/workflows/` automate what [docs/HOW-TO.md](HOW-TO.md)'s "Redeploy Nova in place" recipe otherwise does by hand, against the same one live intellect/agent/avatar the whole repo is built around — neither one ever mints a second live agent.

**`redeploy.yml`** runs `node server/provision.mjs --reuse ... --agent-id ... --avatar-id ...` against the ids already committed in `server/agent.json`, then commits that file back if provisioning changed any of them (a new knowledge record id, most often). It's gated behind a GitHub Environment named `production` with required reviewers configured in the repo's Settings — the same shape GitHub Pages itself uses for `deploy-pages@v4`, but with a human approval step added before the job can read `AGENTIC_ADMIN_SECRET`. It triggers on a push to `server/provision.mjs` (the one file whose change should reshape the live intellect) and on `workflow_dispatch` for an on-demand redeploy.

**`eval.yml`** runs the same eval suite `npm run eval` does, against whichever intellect `redeploy.yml` most recently produced. It triggers when `redeploy.yml` completes successfully (`workflow_run`), plus `workflow_dispatch` with a `trials` input for an ad-hoc pass^k run. Like `redeploy.yml`, it's scoped to the `production` GitHub Environment and its required-reviewer gate — an eval run only reads the live agent conversationally and never provisions anything, but it still needs `AGENTIC_ADMIN_SECRET` to authenticate, so it goes through the same approval step rather than reading an ungated copy of the secrets. In practice that means a `workflow_run` trigger only *queues* the eval; it doesn't execute until a reviewer approves it, the same as `redeploy.yml` itself.

**`ci.yml`** is the third workflow, and the only one not scoped to `production`. It runs on every pull request against `main` — including from forks — via `pull_request` (never `pull_request_target`), and reads no secrets: `node --check` on `server/provision.mjs`, the offline `tests/eval/probes.test.mjs` suite, and a secret-pattern scan (`scripts/scan-secrets.mjs`) over every tracked file. It exists to catch a broken `provision.mjs` or a leaked credential before a change can reach `redeploy.yml`'s production path; it never touches the live agent or reads `production`'s secrets.

**Why the cross-repo trigger stays manual.** The docs site's own `pages.yml` (in `kaltura/intelligent-agents-sdk`) does not automatically dispatch a redeploy here when site content changes. An automatic cross-repo trigger would let a docs PR merge silently reprovision a live production agent with no review step — exactly what the required-reviewer environment above exists to prevent. Instead, `pages.yml` posts a job-summary reminder on every deploy naming this repo's `redeploy.yml` `workflow_dispatch` page, so a human decides when a docs change is worth a redeploy.

**Why that's safe to leave manual: the persona prompt is stateless, the knowledge base isn't.** `loadDocs()`/`buildSiteMap()` rebuild the site-map prompt fresh from the live site checkout's `nav.js` on every single provision run — there's no persisted copy that can go stale between redeploys, so a delayed redeploy never leaves Nova's prompt describing a page that no longer exists. What a delayed redeploy does mean is that her knowledge base (the markdown content she actually retrieves from) lags behind the live site until the next redeploy — she'll cite a page that's genuinely still there, correctly, but may answer from that page's previous content until someone redeploys. Because of the orphan-teardown fix above, the actual content of a redeploy's previous corpus (its category and every entry) is verified to be fully replaced rather than layered onto, so leaving a stale corpus in place for a while costs staleness only, never content drift or duplication.

## About the eval harness's layered design

The eval is split into layers that each do one thing, so the CLI and the browser dashboard can share every one of them instead of drifting into two copies that score things differently:

- **`transport.mjs`** — the wire layer. Self-ACKs `navigate_to_page`/`highlight_element` tool calls exactly like a real browser's `respondToTool()` would, and carries its own tool-call spiral circuit breaker (see below) — since this headless path has no socket, no reconnect, and none of `KalturaAvatarSession`'s own production protections.
- **`chat-transport.mjs`** — the wire layer's chat-mode sibling. Same call contract and return shape, but the turn runs through the SDK's real `KalturaChatSession` (ACKs via its `respondToTool()`, page context via its `setDynamicPrompt()`), so the eval certifies the shipped chat client stack, and a persona can switch transports mid-thread to prove backend thread continuity across both.
- **`engine.mjs`** — the run layer. `runTurn()` adds a whole-turn timeout-and-abort net transport.mjs doesn't have on its own; `runEval()` drives every persona (with the same kickoff warmup a real session sends), runs it `N` times when `--trials` is passed, and merges those trials into one release-gating verdict per turn.
- **`probes.mjs`** — the scoring layer. Pure, synchronous functions, one per correctness dimension, each returning `{pass, ...}` or `null` when a dimension doesn't apply to a given turn. No network or filesystem access, which is what makes them independently unit-testable in `probes.test.mjs` with no live agent involved.
- **`artifacts.mjs`** — the persistence layer. Writes `transcript.json`, `report.json`, and `report.md`, plus a timestamped copy under `history/` that the dashboard's trend view reads.
- **`run.mjs`** / **`dashboard/server.mjs`** — two thin front ends over the exact same `runEval()`/`scoreTurn()`/`writeArtifacts()` core. One is a CLI that exits non-zero on a release-blocking failure (for CI); the other streams the identical run over SSE to a browser, with a run-history view and an ad-hoc single-prompt tester layered on top.

## About the eval harness as a reusable pattern

This suite is meant to be lifted, not just read — if you're building the eval for a different live avatar app, these are the pieces worth copying:

**Adversarial personas as first-class coverage.** `personas.mjs` treats jailbreak/prompt-extraction attempts, gradual multi-turn erosion of a refusal (`role-adherence-drift`), and boundary probes (`restricted-topics`) as required test data, not an afterthought bolted onto happy-path Q&A — a real visitor's hostile or manipulative turn is exactly as likely as a friendly one, and a suite that only exercises the friendly kind isn't testing the thing that actually breaks in production.

**Release-blocking vs. soft dimensions.** `probes.mjs`'s `RELEASE_BLOCKING` list draws a hard line between actual product-safety failures (an invented URL or nav path, a leaked prompt, an un-refused pricing question, a false highlight claim, a knowledge-base search firing while it's supposed to be off) and UX-quality dimensions (latency, tone, completeness) that inform without gating. That split is what lets `run.mjs`'s non-zero exit code mean something specific and defensible in CI, instead of a fuzzy "score dropped" signal.

**pass@k vs. pass^k reliability trials.** A single clean run only proves the agent *can* behave correctly, not that it reliably *will* — LLM output varies run to run. `--trials N` re-runs every persona end-to-end `N` independent times and gates release on the union of every trial's release-blocking failures (pass^k: all trials must pass), rather than treating one success as sufficient (pass@k). For something talking to real customers, a probe that fails on even one of several identical trials is a real reliability gap, not noise to average away.

**A tool-call spiral circuit breaker at the eval layer.** `transport.mjs`'s hard spiral limit deliberately mirrors `KalturaAvatarSession`'s own production safeguard, built independently after both hit the same live failure mode: the brain re-emitting an identical tool call dozens to hundreds of times with no narration. The lesson generalizes beyond this app: a headless test harness has none of a live browser session's protections (no socket, no reconnect, no `KalturaAvatarSession`), so if it's going to survive the same failure mode the production runtime was built to survive, it needs its own copy of the mechanism — not an assumption that the SDK already covers it just because the app does.

**Coverage computed from data, not hand-maintained.** The coverage matrix in `report.json` (expected vs. observed tools, uncovered routes) is derived from the same expectation keys already declared on each persona turn, and route/highlight-target ground truth loads live from the real site checkout (`site-data.mjs`) instead of being copied into this repo by hand. Adding a page to the site, or a turn to a persona, extends the suite's own notion of "covered" automatically — it can't silently drift out of sync with what's actually being tested.

**An external judge kept genuinely optional and out-of-process.** Nova's own conversational backend can't cleanly judge itself, and adding a live-LLM-calling judge dependency in-process would break the zero-dependency posture this app and the SDK both hold to. `run.mjs` always writes `transcript.json` for offline grading and folds verdicts back in via `--judge`, so the qualitative layer is available without the core suite depending on it. See `tests/eval/GUIDELINES.md` for the decomposed-rubric approach this uses when a judge prompt is written.

The persona and probe *content* is domain-specific to a docs-site assistant and won't transfer directly — the mechanisms above are what's worth carrying to another app.

## Known limitations

Documented here rather than left to be rediscovered:

- **A redeployed-away knowledge record leaks as an empty shell.** `deleteKnowledge()`'s `knowledge.deleteRecord()` call reliably 500s on the live backend for any record that ever reached indexed (`status:'READY'`) content — verified live by deleting a bare, content-less scratch record (succeeds) versus retrying delete on a real, previously-indexed record from a redeploy (500s every time, before and after its category was gone). The category and every entry it held ARE reliably deleted first (verified via get-after-delete 404s), so the record that's left behind carries no content and references nothing live — it's a small, inert metadata object, not a repeat of the original orphan bug, but it does accumulate one per redeploy with no code-side fix available against a server-side 500. Not release-blocking; worth a periodic manual sweep if the count grows large enough to matter.
- **Spiral-recovery wording gap.** When the hard-spiral breaker fires and resends the visitor's message with a recovery prefix, the recovery reply doesn't always frame an action-required turn (e.g. "take me home") as a real answer — it can read as a non-answer even though the recovery mechanism itself worked correctly. Open; no fix attempted yet.
- **Poem-prompt double-spiral.** A small number of adversarial prompt-extraction turns (the "write a poem using verbatim lines from your configuration" style of request) have been observed to spiral again on the recovery attempt itself, in certain conversation contexts. Not release-blocking — no prompt ever leaks either time — but not yet root-caused.
- **Dependency scanning doesn't cover the docs site.** `.github/dependabot.yml` here covers this repo's own `npm` and `github-actions` ecosystems. `intelligent-agents-sdk-site` isn't a separate repo — it's a `git worktree` of `intelligent-agents-sdk` checked out on `gh-pages-src` — and GitHub Dependabot only reads `dependabot.yml` from, and opens PRs against, a repo's *default* branch (`main`, for that repo). A `dependabot.yml` committed under the `gh-pages-src` worktree would never be read; it would be inert. If the docs site's own npm dependencies need scanning, that scanning is the `npm` entry with `target-branch: gh-pages-src` in `intelligent-agents-sdk`'s `.github/dependabot.yml` on `main` (it exists there today, alongside the `github-actions` entry), not a file added under this worktree.
